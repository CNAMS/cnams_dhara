# Conflict catalogue

**Status:** Phase 0 deliverable · **Entries:** 1 of 24 · **Source:** roadmap §8, Phase 0

Every concurrent-edit scenario that can occur in a real deployment, with the correct
merged outcome written down before any merge code exists.

---

## What this document is for

This is the specification of correctness. Everything downstream is derived from it:

```
conflict-catalogue.md ──▶ conformance vectors ──▶ Python impl ──▶ Dart impl
        │                        │
        └────────────────────────┴──▶ simulator invariants
```

A scenario missing here will never be generated by the simulator, never covered by a
vector, and both implementations will be confidently wrong about it **in the same
way**. Two implementations agreeing on a scenario neither has considered is not
interoperability; it is a shared blind spot.

**Exit criterion:** for every entry, the desired merged state can be stated field by
field, without hand-waving. If an entry contains the words "sensibly",
"appropriately", or "as expected", it is not finished.

---

## Domain vocabulary in this document

This file describes scenarios in a **real** deployment, so it uses real vocabulary —
weights, names, enrolment. That is the only way the scenarios can be checked against
reality by someone who knows the domain.

The **conformance vectors derived from these entries use neutral field names**, and
so does every line of `dhara`. Each entry therefore names both:

| Domain field | Neutral field id | Lattice |
|---|---|---|
| weight, height, MUAC | `m_a`, `m_b`, `m_c` | `MeasurementSeries` |
| name, guardian phone, address | `d_a`, `d_b`, `d_c` | `LWWRegister` |
| enrolment status | `st_a` | `StatusLattice` |
| risk flags, referrals | `set_a` | `ORSet` |

The mapping from the left column to the middle one lives in the **consumer's**
`schema_binding.py`, never here and never in `dhara`.

## Entry template

```markdown
### C-NN — <short name>

**Setup**           Which replicas, what each did, in what causal relationship.
**Concurrency**     Which operations are concurrent — neither happens-before the other.
**Naive outcome**   What LWW does. Usually: what is silently lost.
**Desired outcome** The exact merged state. Field by field. No prose hedging.
**Lattice**         Which lattice type produces that outcome.
**Review signal**   Emitted or not, and which one.
**Vector**          Path under spec/conformance/ once Phase 1 writes it.
**Open**            Anything genuinely undecided, linked to plan/open-questions.md.
```

**The `Naive outcome` field is mandatory**, and it is the most useful line in each
entry. Writing down what last-write-wins loses, per scenario, *is* the argument of
this project in concrete form — it is what the positioning in roadmap §11 is built
from. An entry where LWW does the right thing is still worth recording: it marks a
place where the extra machinery is not earning anything.

## Entries

### C-01 — Two workers weigh the same child within an hour

**Setup**
Replica A (worker's phone, offline): records weight 9.2 kg at 10:15, `recorded_by=w1`.
Replica B (supervisor's phone, offline): records weight 9.4 kg at 11:40,
`recorded_by=s1`. Both sync at 18:00.

**Concurrency**
Fully concurrent. Neither device has seen the other's operation; neither HLC
descends from the other.

**Naive outcome**
LWW on a `weight` column: 9.4 kg wins the row, **9.2 kg is silently lost**. The
record now asserts that one weighing happened, at a value that is one of two
readings, with no trace of the other.

This is the central failure the project exists to fix. A child's weight is not a
mutable field; it is an event that happened at a time. Two different weights on one
morning is clinically meaningful — bad scale, wrong child, transcription error — and
LWW destroys exactly that information.

**Desired outcome**

| Field | State after merge |
|---|---|
| `m_a` | Two entries, both retained: `{9.2, taken_at=10:15, by=w1}`, `{9.4, taken_at=11:40, by=s1}` |
| ordering | By HLC, deterministic and identical on every replica |
| deletions | None. Neither entry supersedes the other. |

Neither reading is marked correct. The engine has no basis to choose, and inventing
one would be the bug.

**Lattice** `MeasurementSeries` — append-only, deduplicated on
`(taken_at, recorded_by, value)`.

**Review signal** `multiple_weights_same_day` — two measurements of the same field
for the same record on the same calendar day is clinically suspicious and a human
should look.

⚠ "Same calendar day" needs a timezone to be well defined, and the two devices may
disagree about what day it is. The signal is computed against the **record's**
declared timezone from the schema, not either device's local time.

**Vector** `merge/c01_concurrent_measurements_same_day.json`

**Open** None.
